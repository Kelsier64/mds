# G-Maker：從零打造全自動化 AI 短影音生成工作流與本地部署實戰

## 這是什麼&&我學到了什麼
這是我為了探索 AI 媒體生成應用而開發的「全自動化短影音生成系統 (G-Maker)」。這套系統能將任何純文字腳本，全自動轉換為帶有 AI 語音配音、動態字幕，以及完全由 AI 透過 Prompt-to-Video (T2V) 技術即時生成的影片畫面所組成的短影音。

在這個專案中，我最大的突破在於**工作流（Workflow）的模組化設計與實踐**，以及**開源 AI 影片模型的本地部署（Local Deployment）**。我不僅學會了如何使用 Python 的 `uv` 工具進行高效的環境與套件管理，還深入接觸了 SQLite 的狀態管理機制、FFmpeg 的影音自動化剪輯。更重要的是，我成功在本地端部署了 Wan2.2 這樣的重型文字生成影片 (T2V) 模型，並透過自建 API 完美串接進我的系統中，補足了對系統架構設計與邊緣運算的實務經驗。

## 動機與開發起點
近期短影音爆紅，我發現市面上雖然有很多 AI 影音生成工具，但大多是封閉平台且訂閱費高昂。基於對軟體自動化與 AI 生成技術的好奇，我決定自己打造一套端到端的影音生成專案。

起初，我利用免費的 Azure 額度串接 Whisper 與 GPT-4o mini 進行基礎的配音與字幕處理。我的「第一版系統」其實非常陽春：畫面僅依賴ai圖片生成與簡單字幕。然而，當我首度嘗試接入 Azure 的 Sora 模型來生成動態影片時，昂貴的 API 成本讓我第一次測試就把免費額度直接「刷爆」燃燒殆盡。這個痛點迫使我轉換方向，毅然決然投入開源 AI 影片模型的本地部署研究。

## 系統架構與工作流自動化設計 (Workflow)
這專案最讓我有成就感的是其「7 階段自動化工作流」的架構設計。在開發初期，我很快意識到：如果只是寫個腳本依序把 API 呼叫一遍，一旦其中某個環節（例如網路斷線或算圖出錯）失敗，整個流程就會崩潰，導致需要重新啟動並消耗不必要的 API 成本與算力。

因此，我導入了極為重視**狀態管理（State Management）**的思維。我利用 SQLite 建立了一個任務追蹤資料庫（`video_manager.py`），精準記錄每個影片專案的生命週期與處理狀態。
我的自動化工作流包含了：
1. **AI 腳本企劃與提煉 (Script Generation)**：這是系統運作的起點。我設計了一套多層次的 LLM 提示詞工程，能將長文或演講逐字稿自動清洗（去除廢話與口語），並依據短影音（TikTok / YouTube Shorts）的演算法特性，重新潤飾成具備「強烈破題鉤子 (Hook)」與「行動呼籲 (CTA)」、節奏明快的專業腳本。
2. **TTS 語音生成**：接收優化後的腳本，透過 ElevenLabs API 產出逼真人聲，並處理長文本的切割機制。
3. **精準動態字幕**：串接 Whisper 生成逐字稿，這部分我特別將一般 SRT 轉換為 ASS 格式，實現單字等級的動態高光標示。
4. **視覺提示詞生成 (Prompt Generation)**：為了引導影片模型產出穩定高品質的畫面，我設計了 `Subject + Scene + Motion + Aesthetic`（主體+場景+動態+美學）的結構化 Prompt 公式。LLM 會深入分析腳本分鏡與音訊時間軸，判斷需要畫面切換的時機，並精準生成電影級的畫面描述。
5. **AI 影片生成 (Prompt-to-Video)**：將視覺提示詞發送給本地 ComfyUI API 工作流，調用量化過後的 Wan 2.2 開源影片模型進行本機推論算圖，產出切合文意的背景畫面。
6. **多軌影音組裝**：封裝 FFmpeg 的複雜指令，進行圖層疊加、背景模糊與時軌對齊。此外，在後期設計中，我加入了一個自己製作、僅有「開關嘴兩張圖片」的貓咪虛擬主播融入工作流中，專門用來填充沒有 AI 生成影片時的畫面空白。
7. **最終渲染**：燒錄特效字幕並鎖定 60 FPS 輸出影片。

這種高度解耦且具備容錯記錄的設計，讓我在系統出錯時能優雅地攔截例外（Exception），且重啟時系統能自動接續未完成的節點，不用反覆浪費資源重新執行。我在終端機也利用了客製化的 UI 與 Loading Spinner 改善整體流程的監控體驗。

## 本地部署的挑戰與硬體效能優化 (Local Deployment & Optimization)
在失去昂貴的雲端影片 API 後，我決定挑戰將強大的開源模型 **Wan 2.2** 部署於地端。這是我第一次處理需要極端 GPU 算力的深度學習模型，因此我借用了同學配備 16GB 顯卡的高性能電腦，將其作為算力節點架設 API 供系統調用。

一開始的光景可說是災難一場。我遭遇了無止盡的環境建置地獄：從 PyTorch 衝突、NVIDIA Toolkit 與 CUDA 不匹配，一路到令人崩潰的 flash_attn 編譯錯誤。且即便環境裝好，受限於 16GB VRAM，我也只能勉強跑得動參數最低的模型，產出的畫面時常扭曲崩壞，且算圖效率極低，生成短短 5 秒的影片片段竟需要耗費高達 5 分鐘。

為了解決資源瓶頸與品質問題，我開始深入研究模型優化技術。我捨棄了官方基礎腳本，改導入 **ComfyUI 與社群高度優化的量化工作流**；接著在後端利用 Python 串接其 API。這項改動是巨大的轉捩點：它大幅壓縮了顯存占用，讓我終於能在那張 16GB 顯卡上順利推論「具備更好畫質」版本的影片模型，明顯提升了影片品質。這項實戰讓我深刻體會到，懂得如何進行硬體資源調度來突破物理極限，與寫出漂亮的程式邏輯一樣重要。

## 總結與自我探索
開發 G-Maker 的過程完全打破了我對單純寫程式碼的狹隘認知。從導入 SQLite 實踐狀態追蹤，到熬夜死磕環境部署與架設地端計算 API，這個專案將我推向了系統架構與基礎維運的實戰領域。

儘管過程中充滿著環境部署與效能瓶頸的挫折，且目前的 AI 影片生成仍有一定機率產出糟糕的畫面或是單純非常耗時，但這套工作流最終還是順利地運作了起來。我將這套全自動化系統產出的影片上傳至 YouTube，最終累積了五萬多次的觀看。這雖然談不上是龐大的流量，但也給了我一點能夠透過科技產出實際受眾內容的小小成就感。這過程中我清楚看見系統中還有極多細節可以優化，這次專案證明了我具備從無到有全端除錯並學習的能力，未來我也將繼續研究這套系統在 Docker 容器化與生成效率上的無盡升級空間。
